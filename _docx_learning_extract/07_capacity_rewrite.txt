아래는 지금까지 논의한 내용을 농협 상호금융 정보계 NSIGHT 용량산정 및 환경 설정 기준으로 다시 정리한 최종본입니다. 기준은 VM 1대 = 250 TPS 처리 기준, 목표 응답시간 p95 3초, AP Active-Active, 은행 정보계 전용 단말/WebTopSuite 사용을 전제로 합니다.
1. 전체 기준 요약
핵심은 세션 수와 TPS를 분리해서 보는 것입니다.
세션 수 = 로그인 상태로 유지되는 사용자 수
TPS = 실제 동시에 거래를 요청하는 처리량
2. 사용자·세션 기준
농협 상호금융 정보계의 기본 사용자는 다음과 같이 산정합니다.
3,600개 지점 × 6명 = 21,600명
여기에 운영 여유율 20~30%를 반영하면 다음과 같습니다.
따라서 전체 시스템은 최대 약 28,000 세션 수용을 기준으로 설계합니다.
3. VM 250 TPS 기준 TPS 산정
목표 응답시간을 3초로 볼 때 TPS는 다음과 같이 산정합니다.
TPS = 동시 요청자 수 ÷ 목표 응답시간
따라서 기준은 다음과 같이 잡는 것이 적절합니다.

은행 정보계 전용 단말/WebTopSuite 기준에서는 일반 웹처럼 30분 세션은 짧습니다.

단, 세션에는 반드시 최소 정보만 저장해야 합니다.
8. HTTP Connection과 Session 관계
중요한 결론은 다음입니다.
Connection은 통신 통로이고, Session은 로그인 상태입니다.
따라서 Tomcat의 connectionTimeout, keepAliveTimeout으로 연결이 끊겨도 세션이 끊기는 것은 아닙니다.
로그인 성공
↓
Tomcat Session 생성
↓
JSESSIONID 발급
↓
WebTopSuite가 JSESSIONID 저장
↓
HTTP 연결은 Timeout으로 종료 가능
↓
다음 거래 시 새 연결 생성
↓
기존 JSESSIONID 쿠키 전달
↓
Tomcat은 기존 세션 조회
즉, 거래 요청 시 기존 연결이 살아 있으면 재사용하고, 끊겼으면 새 연결을 맺되 기존 JSESSIONID를 보내면 세션은 유지됩니다.

10. Tomcat Thread와 TPS 관계
VM당 250 TPS를 처리하려면 평균 응답시간이 중요합니다.
필요 Busy Thread ≒ TPS × 평균 응답시간
따라서 중요한 결론은 다음입니다.
p95 응답시간은 3초 이하로 관리하되, VM당 250 TPS를 달성하려면 평균 응답시간은 1.0~1.2초 수준이어야 한다.

18. 최종 결론
농협 상호금융 정보계 NSIGHT 온라인 AP 용량산정은 VM 1대당 250 TPS를 기준으로 정비한다. 전체 사용자 21,600명, 여유율 포함 26,000~28,000 세션을 기준으로 하며, 동시 요청률 10% 피크 시 720 TPS를 목표로 산정한다. AP Active-Active와 센터 장애 대응을 고려하면 피크 기준 센터당 4대, 전체 8대가 적정하며, 스트레스 1,080 TPS까지 보장하려면 센터당 6대, 전체 12대가 필요하다. Tomcat은 maxThreads 500, minSpareThreads 100, acceptCount 200, maxConnections 8192, keepAliveTimeout 60초를 기준으로 하고, JVM은 12~14GB Heap과 G1GC, Hikari Pool은 일반 50개·SingleView 60개를 1차 기준으로 적용한다. 단, 이 기준은 평균 응답시간 1.0~1.2초, p95 3초 이하, DB SQL 평균 100~300ms, Hikari 사용률 70~80% 이하, Tomcat Busy Thread 70~80% 이하가 성능테스트에서 확인된다는 조건에서 유효하다.
