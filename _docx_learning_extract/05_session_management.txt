아래는 NSIGHT 마케팅플랫폼 세션 아키텍처 정리본입니다. 전제는 명확합니다.
센터 간 접속은 GSLB 기반 DNS Lookup으로 센터 L4를 선택하고, WebTopSuite 단말은 선택된 센터 L4에 직접 접근한다. 세션은 센터 내부 Tomcat Cluster의 DeltaManager로 복제한다. 센터 간 세션 복제는 기본 적용하지 않는다.
NSIGHT 세션 아키텍처 설계서
GSLB + WebTopSuite 직접 L4 접근 + Tomcat DeltaManager 기준
1. 설계 목적
NSIGHT 마케팅플랫폼은 WebTopSuite 단말을 사용하고, 사용자는 센터 간 GSLB를 통해 최초 접속 센터를 결정한 뒤 해당 센터의 L4를 통해 마케팅 AP 또는 싱글뷰 AP에 접근한다.
따라서 세션관리는 다음 목적을 만족해야 한다.

3. 핵심 설계 결정
4. GSLB 기준 접속 설계
4.1 GSLB의 역할
GSLB는 매 요청을 처리하는 Gateway가 아니다. NSIGHT 구조에서 GSLB의 역할은 최초 센터 선택이다.
중요한 점은 DNS Lookup은 센터 ID를 직접 반환하는 것이 아니라 일반적으로 L4 VIP를 반환한다는 것입니다. 따라서 WebTopSuite가 L4 VIP와 CENTER_ID를 매핑해야 합니다.
4.2 CENTER_ID 매핑 방식
GSLB Lookup 결과
10.10.10.100 → CENTER_1
10.20.10.100 → CENTER_2
5. WebTopSuite 단말 처리 로직
5.1 최초 기동 및 로그인 흐름
1. WebTopSuite 기동
2. GSLB DNS Lookup 수행
3. 센터 L4 VIP 반환

6. 해당 센터 L4로 로그인 요청
7. L4가 센터 내부 AP로 라우팅
8. 로그인 성공
9. JSESSIONID 발급
10. Tomcat DeltaManager가 센터 내부 AP Cluster에 세션 복제
5.2 정상 업무 요청 흐름
1. WebTopSuite가 저장된 CENTER_L4_URL 확인
2. CENTER_L4_URL로 업무 요청 전송
3. L4 Sticky 기준으로 기존 AP에 요청 전달
4. AP가 JSESSIONID 기준 세션 확인
5. 업무 처리
6. RDW 조회 또는 CruzAPIM 연계 수행
7. 응답 반환
5.3 센터 장애 감지 흐름
1. WebTopSuite가 현재 CENTER_L4_URL 호출
2. 접속 실패 또는 Timeout 발생
3. 동일 센터 L4 재시도 1~2회
4. 실패 지속 시 GSLB DNS 재조회
5. 대체 센터 L4 VIP 수신
6. CENTER_ID 변경
7. 사용자에게 재로그인 안내
8. 대체 센터로 로그인 후 업무 재개
6. Tomcat DeltaManager 세션 설계
6.1 DeltaManager 적용 목적
Tomcat DeltaManager는 동일 Tomcat Cluster 내 세션 변경분을 복제하여 AP 장애 시 세션 유실을 줄이는 방식이다.
[AP-01 세션 생성]
↓
[DeltaManager]
↓
[AP-02에 세션 복제]
AP-01 장애 시 L4가 AP-01을 제외하고 AP-02로 라우팅하면, AP-02는 복제된 세션을 사용해 업무를 이어갈 수 있다.
6.2 적용 범위
6.3 Cluster 분리 기준
마케팅 AP와 싱글뷰 AP는 하나의 DeltaManager Cluster로 묶으면 안된다.
권고 문장:
DeltaManager는 사용자 화면 요청을 처리하는 AP Cluster에만 적용한다.
7. L4 Sticky와 DeltaManager 관계
L4 Sticky와 DeltaManager는 대체 관계가 아니라 보완 관계입니다.
정상 시에는 Sticky로 세션 이동을 줄이고, 장애 시에는 DeltaManager로 동일 센터 내 세션 연속성을 확보합니다.

8.4 센터 복구 후 Failback
센터 복구 후 즉시 원복하면 세션 혼선이 발생할 수 있습니다.
권고:
Failback은 강제 세션 이동이 아니라 신규 접속 중심의 점진적 원복으로 수행한다.
9. 세션 데이터 설계
DeltaManager를 사용할 경우 세션 크기가 매우 중요합니다. 세션이 커지면 복제 부하가 증가하고 AP 성능이 떨어집니다.
