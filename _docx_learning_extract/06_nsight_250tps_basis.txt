아래는 VM당 처리량을 250 TPS 기준으로 다시 정리한 NSIGHT 용량산정 기준입니다. 핵심은 기존과 동일하게 세션 수는 전체 사용자 기준, TPS·Thread·DB Pool·서버 수는 동시 요청자 기준으로 분리하는 것입니다. NSIGHT 변경 기준은 전체 사용자 21,600명, 설계 세션 26,000~28,000, 목표 응답시간 3초, 5%/10%/15% 동시 요청률 기준으로 정리합니다.
NSIGHT 용량산정 기준
8 vCPU / 32GB VM, VM당 250 TPS 기준
1. 기준에 따른 동시 요청자 / TPS 산정
1.1 기본 전제
1.2 산정 공식
동시 요청자 = 전체 사용자 수 × 동시 요청률
TPS = 동시 요청자 ÷ 목표 응답시간

2. 전체 환경 설정 기준 요약
2.1 VM
주의할 점은 250 TPS/VM은 “모든 거래가 평균 3초 걸려도 250 TPS를 낸다”는 뜻이 아닙니다. 3초는 목표 응답시간 또는 p95 기준으로 보고, 실제 평균 응답시간은 1초 내외~1.5초 수준으로 관리되어야 8 vCPU VM에서 250 TPS 기준이 현실적입니다. 기존 기준에서도 8 vCPU / 32GB VM은 Java/Tomcat 기반 정보계 AP의 Scale-Out 단위이며 Core당 30~40 TPS, VM당 약 250 TPS 산정 기준으로 정리되어 있습니다.

3. 서버 수 기준
3.1 AP 수 산정
3.1.1 단순 TPS 기준 산정
필요 VM 수 = 목표 TPS ÷ VM당 TPS
단순 계산만 보면 720 TPS는 3대, 1,080 TPS는 5대면 됩니다. 그러나 운영에서는 센터 이중화, AP 장애, 배포 중 제외, DeltaManager Cluster, N+1 여유를 반영해야 하므로 단순 필요 VM보다 크게 잡아야 합니다.

5. TOMCAT 설정
5.1 세션 설정
세션은 TPS를 직접 증가시키지 않습니다. 세션 시간이 길어질수록 오래 살아 있는 Active Session과 DeltaManager 복제 대상이 늘어나므로, 세션 데이터는 반드시 작게 유지해야 합니다.
5.2 DeltaManager 설정
Tomcat DeltaManager는 센터 내부 AP Cluster에 한정해 적용하고, 센터 장애 시에는 기본적으로 재로그인 정책을 적용하는 것이 운영 단순성과 장애 격리 측면에서 적절합니다.
5.3 Tomcat 실행 Thread
5.3.1 산정 관점
필요 Thread 수 = VM당 TPS × 평균 응답시간 × 여유율
다만 여기서 응답시간은 항상 3초 평균으로 보면 안 됩니다. 3초를 평균으로 잡으면 250 TPS/VM 기준 필요 Thread가 750개 이상이 되어 8 vCPU VM에서 Context Switching과 메모리 부담이 커집니다.
